Логирование — это автоматический журнал запусков. Каждый раз, когда ты запускаешь обучение, в таблицу `EXPERIMENTS.csv` добавляется одна строка про этот запуск.

## Как это выглядит

1. **Ты запускаешь скрипт** (например, `train_gine.py`). В первую же секунду в таблице появляется строка со статусом `running`. В ней уже записаны скрипт, параметры, seed и версия данных.
2. **Скрипт работает** (минуты или часы). Строка просто висит со статусом `running`.
3. **Скрипт заканчивается**, и эта же строка обновляется:
   - `ok`, если всё прошло, плюс метрики и путь к логу;
   - `failed`, если была ошибка, плюс текст ошибки;
   - `interrupted`, если ты остановила скрипт через Ctrl+C.

Новых строк при этом не добавляется, обновляется та же самая.

## Что хранится в строке

| Колонка | Что там |
|---|---|
| date | когда запустили |
| script | какой скрипт |
| params | все параметры запуска (эпохи, batch size, lr и так далее) |
| seed | seed |
| data_version | хэш файла с данными, чтобы было видно, на каких данных считали |
| metrics | результаты |
| log_path | где лежит подробный лог |
| status | running / ok / failed / interrupted |
| notes | заметки, например путь к модели или текст ошибки |

## Что нужно помнить

- **Если процесс убили насильно** (закрыли окно, выключили питание, `kill`), скрипт не успеет обновить строку. Она так и останется `running`. Такая строка без живого процесса значит, что запуск оборвался. Перед сдачей поменяй её статус вручную на `failed`.
- **Excel держи закрытым.** Если таблица открыта в Excel, запись не получится. Скрипт напишет предупреждение, но обучение не упадёт, просто строка не обновится.
- **Два запуска одновременно** допустимы. Они не затрут записи друг друга.
- **Неудачные запуски тоже попадают в таблицу.** Этого и требует задание.

## Как это устроено внутри

В [experiments/log_run.py](experiments/log_run.py) есть блок `tracked_run`. Он оборачивает основную работу скрипта:

```python
with tracked_run("train_gine.py", params=..., seed=42, dataset_path=csv) as run:
    ...  # здесь идёт обучение
    run.set(metrics={...})  # здесь мы сообщаем метрики
```

- В начале блока запись добавляется со статусом `running`.
- В конце, при нормальном выходе, ставится `ok`. При ошибке `failed`. При Ctrl+C `interrupted`.
- Этот блок я вставила в `train_gine.py`, `run_splits.py`, `predict_gine.py` (в обеих версиях GINE), в RelGAN и в Diffusion-LM. Новые скрипты для задач 1–4 будем писать так же.

## Общая идея (одной фразой)

Скрипт превращает каждую строку датасета в «отпечаток» последовательности API-вызовов (хэш), а потом считает, сколько раз каждый отпечаток повторяется и в каких классах.

## Что делает каждая часть

### 1. `parse_args()` — параметры запуска
Три параметра, у каждого есть значение по умолчанию:
- `--csv` — путь к датасету, по умолчанию MalBehavD-V1;
- `--out-dir` — куда класть результаты, по умолчанию `derived/`;
- `--log` — куда писать текстовый отчёт.

Поэтому скрипт запускается без аргументов. Тот же скрипт можно запустить и на другом датасете, если формат такой же.

### 2. `api_columns(df)` — какие колонки содержат вызовы
В CSV формат «широкий»: одна строка — один файл, колонки `0, 1, 2, …` — позиции вызовов. Колонки `sha256` и `labels` служебные.

Особенность датасета: колонки 155–176 в CSV не имеют заголовка. pandas называет их `Unnamed: 155` и так далее. В них тоже вызовы, поэтому функция берёт и чисто цифровые колонки, и `Unnamed`. Без этого длинные последовательности обрезались бы на 155-м вызове.

### 3. `row_sequence(values)` — последовательность одной строки
Трассы разной длины, а колонок 175. У короткой трассы хвост пустой (NaN). Функция оставляет только непустые строковые значения.

Пропусков в середине последовательности нет. Я проверила это отдельно перед написанием скрипта, поэтому выбросить пустые значения означает ровно «обрезать хвост».

### 4. `build_hashes(df)` — главный шаг
Для каждой строки:
1. собирает последовательность (`row_sequence`);
2. склеивает вызовы через пробел: `"LdrLoadDll NtOpenFile NtClose …"`;
3. считает от этой строки **sha256**.

Результат — таблица `hashes.csv` с колонками:
- `row_idx` — номер строки в исходном CSV, чтобы потом найти её;
- `sha256_file` — хэш исполняемого файла, взят из датасета;
- `label` — класс: 0 означает benign, 1 означает malware;
- `seq_hash` — хэш последовательности;
- `seq_len` — длина последовательности.

**Зачем хэш, а не сравнивать сами последовательности?** Хэш — короткая строка фиксированной длины. Одинаковые последовательности дают одинаковый хэш, разные с практической гарантией дают разный. Сравнивать и группировать 64 символа гораздо проще, чем списки до 175 элементов. Этот же хэш потом станет «группой» в задаче 3.

**Почему склеиваем через пробел?** Чтобы границы между вызовами сохранились. В именах API пробелов нет, это тоже проверено. Значит, разные последовательности не склеятся в одинаковую строку.

**Важно не перепутать два хэша:**
- `sha256_file` — отпечаток **файла** (программы);
- `seq_hash` — отпечаток **поведения** (того, какие вызовы программа сделала в песочнице).

Два разных файла могут вести себя одинаково, и это и есть дубли поведения. Один и тот же файл может дать разное поведение при повторном запуске: в датасете таких 11 случаев.

### 5. `summary_table(h)` — сводная таблица
Сначала считаются вспомогательные вещи:
- `group_size` — для каждой строки размер её группы, то есть сколько строк с таким же `seq_hash`. Используется `groupby(...).transform("size")`: размер группы записывается обратно в каждую строку;
- `in_dup` — строка входит в группу дублей, если размер группы ≥ 2;
- `conflict_hashes` — хэши, у которых в группе больше одной уникальной метки (`nunique() > 1`), то есть одна последовательность размечена и как benign, и как malware;
- `file_dup` — строки, у которых `sha256_file` встречается больше одного раза.

Внутренняя функция `by_class` считает одно и то же три раза: по всему датасету, только по benign и только по malware. Её можно вызвать двумя способами:
- с маской (`mask`): посчитать, сколько строк, где условие верно;
- с функцией (`func`): применить её к подтаблице, например посчитать уникальные хэши.

Строки таблицы и как они считаются:

| Строка | Как считается |
|---|---|
| Всего строк | `len` подтаблицы |
| Уникальных последовательностей | число разных `seq_hash` в подтаблице |
| только в этом классе / общих для обоих | разность множеств: уникальные хэши класса минус конфликтные |
| Строк в группах дублей | сколько строк с `in_dup` |
| Лишних копий | строк минус уникальных. Если удалить дубли, оставив по одной копии, уйдёт столько строк |
| Последовательностей с разными метками | число конфликтных хэшей |
| Строк с конфликтующими метками | сколько строк принадлежит этим хэшам |
| Строк с повторяющимся sha256 файла | маска `file_dup` |

**Тонкость, с которой вышла путаница с суммой.** Уникальные считаются отдельно в каждом классе. Конфликтная последовательность уникальна и в benign, и в malware, поэтому учитывается дважды. Отсюда 1123 + 479 = 1602, а не 1601. Две строки «из них…» разводят это явно.

### 6. `top_groups(h)` — 5 крупнейших групп
`groupby("seq_hash")` собирает по каждому хэшу:
- `size` — размер группы;
- `benign`, `malware` — сколько строк каждого класса;
- `seq_len` — длина последовательности, одинаковая внутри группы;
- `example_row` — номер первой строки группы, чтобы можно было открыть её в CSV.

Группы сортируются по размеру, при равенстве по номеру строки, чтобы порядок был воспроизводимым. Берутся первые 5. Хэш обрезан до 12 символов для читаемости.

### 7. `main()` — сборка всего вместе
1. Создаёт папки, если их нет.
2. Открывает `tracked_run`: в `EXPERIMENTS.csv` появляется строка со статусом `running`.

**Группа дублей** — это все строки, у которых одинаковый `seq_hash`, то есть полностью совпадает последовательность API-вызовов. Группа из одной строки — это уникальная последовательность. Группа из двух и больше строк — группа дублей.

## Две метрики

**«Строк в группах дублей (группа ≥ 2)»** — сколько строк датасета входят в группы, где копий несколько. Считаются все строки группы, включая первую.

**«Лишних копий (строк − уникальных)»** — сколько строк можно выбросить, оставив по одному представителю от каждой последовательности. Это число строк минус число уникальных последовательностей.

## Пример на пальцах

Пусть есть 6 строк с последовательностями: A, A, A, B, B, C.

| | значение |
|---|---|
| Всего строк | 6 |
| Уникальных последовательностей | 3 (A, B, C) |
| Групп дублей | 2 (A из 3 строк, B из 2 строк) |
| **Строк в группах дублей** | 3 + 2 = **5** (C одиночная, не считается) |
| **Лишних копий** | 6 − 3 = **3** (две лишние A и одна лишняя B) |

## Что это значит на наших числах

| | всего | benign | malware |
|---|---|---|---|
| Строк | 2570 | 1285 | 1285 |
| В группах дублей | 1157 | 242 | 915 |
| Лишних копий | 969 | 162 | 806 |

- **В группах дублей** отвечает на вопрос «какая доля данных вообще повторяется». У malware это 915 из 1285 строк, то есть около 71%. У benign 242 из 1285, около 19%.
- **Лишние копии** отвечают на вопрос «сколько данных можно удалить без потери информации». У malware можно убрать 806 строк, и останется 479 разных последовательностей. У benign убирается всего 162.

Разница между числами в строках 242 и 162 (и 915 и 806) — это «первые экземпляры» групп. Например, у malware 915 − 806 = 109 групп дублей: из каждой одна строка остаётся, остальные лишние.

## Какое число для чего использовать

- Говоря о масштабе проблемы («какая часть датасета повторяется»), опирайся на **строки в группах дублей**.
- Говоря об эффективном размере данных («сколько настоящих разных примеров»), опирайся на **уникальные последовательности** и **лишние копии**.

Эти строки связаны так: лишние копии = строки в группах дублей − число групп дублей. Проверь для malware: 915 − 109 = 806.

## Как считается

Для каждой eval-строки скрипт проверяет, есть ли в train пара (хэш последовательности, метка) с теми же значениями. Доля таких строк среди всех eval-строк и есть этот параметр.

Утечка вредна, когда модель может просто вспомнить ответ. Это возможно, если копия в train имеет ту же метку, что и eval-строка. Если метка в train другая, копия не подсказывает ответ, а наоборот сбивает модель.

## Что такое утечка в этом контексте

Утечка (data leakage) — это когда информация из проверочных данных попадает в обучение. Модель на проверке встречает то, что уже видела при обучении, и показывает результат лучше, чем покажет на новых данных.

У нас утечка устроена так: одна и та же последовательность API-вызовов оказывается и в train, и в eval. Модель могла просто запомнить её вместе с ответом, а не научиться отличать вредоносное поведение от безобидного. Метрики тогда измеряют память, а не способность обобщать.

## Как работает сбалансированная раскладка (для защиты)

После исключения конфликтной последовательности каждая группа целиком принадлежит одному классу. Поэтому классы раскладываются по отдельности:
1. Группы класса сортируются от больших к меньшим. Группы одного размера идут в случайном порядке, который задаётся seed.
2. Каждая следующая группа кладётся в фолд, где строк этого класса пока меньше всего. Это жадный алгоритм, он называется LPT.
3. Номера фолдов случайно перемешиваются с seed, поэтому test и val каждый раз достаются разным группам.

У этого способа есть особенность, которую стоит знать: 5 крупнейших групп malware всегда оказываются в 5 разных фолдах. Значит, в test всегда ровно одна из них.

## Что такое словарь в GINE

Словарь сопоставляет каждому имени API номер: `NtOpenFile → 17`, `LdrLoadDll → 42` и так далее. Номер 0 зарезервирован за `<UNK>`, то есть «неизвестный вызов».

В GINE каждый вызов в трассе — это узел графа. Признак узла — вектор длины «размер словаря»: везде нули, а единица стоит на позиции номера этого API (one-hot). Размер словаря поэтому определяет размер входа модели.

## Что меняется

**Было:** словарь собирался по всем данным, включая test.
**Стало:** словарь собирается только по train.

Отсюда три следствия.

### 1. API, встречающиеся только в val/test, становятся `<UNK>`

- **Раньше** у такого API был свой номер, но модель ни разу не видела его при обучении. Веса для его позиции фактически не обучались: оставались почти случайными после инициализации.
- **Теперь** он кодируется как `<UNK>`. Модель видит «какой-то незнакомый вызов».

Важная деталь: `<UNK>` в train тоже не встречается, потому что все API из train в словаре есть. Значит, и его веса не обучены. Поэтому на точности это скорее всего отразится слабо. На пробной выборке так оказались только 2 API из 245.

### 2. Меняется размер модели и случайная инициализация

Словарь меньше, значит, меньше первый слой модели. Генератор случайных чисел при том же seed выдаёт другие начальные веса. Из-за этого метрики будут немного отличаться от прежних прогонов, даже если разбиение то же самое.

**Вывод:** старые и новые результаты напрямую сравнивать нельзя. Все прогоны для задачи 4 нужно делать на новом коде.

### 3. В протоколе B эффект сильнее, чем в A

- **В A** почти любая последовательность из test имеет похожих «соседей» в train, поэтому незнакомых API почти нет.
- **В B** последовательности из test в train никогда не встречались. Доля незнакомых API там выше.

Это не недостаток, а честное приближение к реальности: новый malware может вызывать функции, которых детектор раньше не видел. Модель, обученная на старом словаре, получит их как `<UNK>`, ровно как будет в работе.

## Главное

Правка нужна прежде всего для **методической корректности**, а не ради изменения цифр. При словаре по всем данным информация о test (какие API в нём есть) попадала в модель до проверки. Это маленькая, но всё же утечка, и правило руководителя запрещает её.

Насколько изменятся метрики, заранее точно сказать нельзя. Скорее всего немного. Точный ответ можно получить, посчитав в задаче 4, сколько API из test отсутствует в словаре train для протоколов A и B. Я могу добавить эту цифру в отчёт скрипта задачи 4, она пригодится и для текста.

## `seqs_in_several_parts`

Пример: последовательность X встречается в датасете 10 раз. 7 копий попали в train, 3 в test. X «разорвана» между частями, и она добавляет 1 к `seqs_in_several_parts`.

## 2) TF-IDF, n-граммы, логистическая регрессия

**n-граммы.** Это подряд идущие кусочки трассы длиной n. Для трассы `NtOpenFile NtReadFile NtClose` получится:
- 1-граммы: `NtOpenFile`, `NtReadFile`, `NtClose`;
- 2-граммы: `NtOpenFile NtReadFile`, `NtReadFile NtClose`;
- 3-грамма: `NtOpenFile NtReadFile NtClose`.

Одиночные вызовы говорят только о том, *что* программа вызывает. Короткие цепочки сохраняют немного порядка вызовов, например «открыл → прочитал → закрыл».

**TF-IDF.** Каждую трассу он превращает в вектор, где у каждой n-граммы свой вес:
- **TF** (term frequency): как часто n-грамма встречается в этой трассе.
- **IDF** (inverse document frequency): `log(N / df)`, где df — в скольких трассах train встречается эта n-грамма. Если цепочка есть почти в каждой трассе (типичный старт процесса), вес маленький. Если она встречается редко, вес большой.
- Итоговый вес = TF × IDF, потом вектор нормируется по длине (L2), чтобы длинные трассы не перевешивали короткие.

**Логистическая регрессия.** Это линейная модель: она считает `z = w·x + b` и переводит z в вероятность malware через сигмоиду `p = 1 / (1 + e^(−z))`. У каждой n-граммы свой вес w: положительный тянет к malware, отрицательный к benign. Обучение подбирает такие w, чтобы минимизировать log-loss плюс штраф за большие веса (L2-регуляризация). Параметр **C** — это обратная сила штрафа: при маленьком C модель простая и веса прижаты к нулю, при большом C модель сильнее подстраивается под train.

- [строка 50](experiments/baseline_tfidf.py#L50): `TfidfVectorizer(token_pattern=r"\S+", lowercase=False, ngram_range=(1, 3), sublinear_tf=True)`

H1 — это не метрика, а **гипотеза** из плана руководителя:

> **H1: при протоколе A (случайное разбиение) метрики выше, чем при протоколе B (групповое разбиение, где одинаковые трассы не попадают одновременно в train и test).**

Смысл такой: если одни и те же трассы лежат и в train, и в test, модель частично «узнаёт» уже виденные примеры, и оценка получается завышенной. Проверить H1 значит выяснить, падают ли метрики, когда эту утечку убирают.

Никакой отдельной метрики «H1» нет. [h1_table.py](experiments/h1_table.py) берёт обычные метрики и сравнивает их между протоколами.

**Какие метрики сравниваются** ([строка 25](experiments/h1_table.py#L25)):
- **MCC**: главная метрика, учитывает все четыре клетки матрицы ошибок;
- **PR-AUC** и **ROC-AUC**: качество ранжирования, от порога не зависят;
- **F1**;
- **FPR@TPR=0.95**: доля benign, ложно отмеченных как malware, когда ловится 95% malware. Здесь меньше значит лучше.
- Каждая из них считается ещё и в варианте `dedup_*`: на test, где каждая уникальная трасса учтена один раз.

**Что считает скрипт:**
1. Для каждой пары «модель × протокол» берёт среднее ± std по 5 seed. Результат в `h1_table.csv` и `.md`.
2. Для каждой модели и метрики считает разницу (`h1_diff.csv`, [строки 53–62](experiments/h1_table.py#L53-L62)):
   - `diff_A_minus_B`: среднее A минус среднее B. Если она > 0 (для FPR < 0), A выглядит лучше, что согласуется с H1.
   - `diff_to_max_std`: во сколько раз разница больше разброса по seed. Если меньше 1, разница тонет в случайном шуме.
   - `A_better`: True или False.
   - `welch_p`: p-value t-теста Уэлча. При 5 seed на группу тест слабый, это только ориентир.

**Как читать результат.** H1 подтверждается, если для обеих моделей A стабильно лучше B, причём разница заметно больше разброса по seed. Сильнее всего это должно проявиться на MCC и `dedup_*`. Решение, подтвердилась ли H1, скрипт не принимает: вывод делаешь ты по этим числам.

Разница в том, **как считаются одинаковые трассы внутри test**.

**«Все строки test».** Каждая строка считается отдельным примером, даже если её трасса полностью совпадает с другими. Если в test 164 копии одной трассы, модель как будто сдаёт 164 примера, хотя на деле это один и тот же пример.

**«Дедуплицированный test»** (`dedup_*`). Из каждой группы одинаковых трасс (одинаковый `seq_hash`) остаётся одна строка, первая по порядку ([eval_utils.py:99](experiments/eval_utils.py#L99)). Так каждая уникальная трасса учитывается один раз.

**Пример.** В test 100 строк: 60 разных трасс и одна трасса, повторённая 40 раз.
- Если модель верно классифицирует эту повторяющуюся трассу, в «всех строках» это сразу 40 верных ответов, и метрика заметно растёт.
- Если ошибается, это сразу 40 ошибок.
- В дедуплицированном test эта трасса даёт один ответ из 61.

Модель видит одинаковый вход, поэтому выдаёт для всех копий одну и ту же вероятность. Копии не добавляют новой информации о качестве модели, только меняют вес одного примера.

**Почему это важно для нас.** В протоколе B группы целиком попадают в одну часть. Из-за этого крупные группы иногда целиком оказываются в test: при seed 44 одна группа из 164 строк — это примерно 64% malware в test. Тогда метрика по «всем строкам» во многом говорит о том, угадала ли модель одну эту трассу. Дедуплицированный test убирает этот перекос и показывает, как модель справляется с *разными* трассами.

**Как читать таблицы:**
- «Все строки» — это стандартный способ, именно так обычно и считают в статьях.
- `dedup_*` — более честная оценка обобщения: «сколько разных поведений модель распознаёт».
- Если между ними большой разрыв, значит повторы сильно влияют на итоговую оценку. Это стоит отметить, когда будешь интерпретировать H1.


2. **Пакеты, поставленные через conda, `pip freeze` часто пишет без версий**, в виде `numpy @ file:///C:/b/abs_.../...`. Восстановить по такой строке на другой машине нельзя. Нормальные версии `пакет==версия` даёт другая команда:

   ```
   pip list --format=freeze > requirements-freeze.txt
   ```

   ```
   conda env export --no-builds > environment.yml
   ```

   ```
   pip list --format=freeze | Out-File -Encoding utf8 requirements-freeze.txt

   ```

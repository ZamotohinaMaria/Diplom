# 1. Кратко

1. **DataCon 2019 Stage1 переведён в формат MalBehavD-V1** (`sha256, labels, 0, 1, …`) в двух вариантах: raw — все записи песочницы, clean — без служебных записей. Все 30 000 файлов разобраны без ошибок, метки совпали с папками, из clean выпала одна строка.
2. **Датасет в 12 раз больше MalBehavD-V1** (30 000 строк против 2570), классы 2 : 1 (20 000 benign, 10 000 malware). Последовательности короче: медиана 15 API в clean против 37 в MalBehavD. Словарь меньше: 81 API против 291.
3. **Дублей больше, чем в MalBehavD-V1:** уникальны только 30,7 % строк clean (в MalBehavD — 62,3 %). Но повторяется в основном **benign**: уникальны 22,7 % benign и 47,2 % malware. В MalBehavD было наоборот.
4. **Конфликтующих меток много:** в clean 2010 строк (6,7 %) приходятся на 56 трасс, которые встречаются и как benign, и как malware. В raw таких строк 516; удаление служебных записей склеивает трассы и увеличивает число конфликтов. В MalBehavD-V1 конфликтных строк было 12.
5. **Сильные признаки-«подсказки»:** размер XML-отчёта или общее число вызовов сами по себе разделяют классы с ROC-AUC около 0,90. Это выше, чем длина clean-последовательности (0,75), которую модель видит на входе.
6. **Каждый файл в датасете встречается один раз** (повторных `sha256` нет). Поэтому протокол C на DataCon совпадает с B: группировка по файлу ничего не добавляет к группировке по трассе.
7. **Словари почти не пересекаются:** из 81 API DataCon в MalBehavD-V1 есть 53. Перенос модели между датасетами возможен только на общих API.

**Структура одного отчёта.** XML песочницы: `report` → `file_list` (имя исследуемого файла) → `file` → разделы `start_boot` (поведение после запуска) и, у части файлов, `reboot` (поведение после перезагрузки) → `action_list` → `action`. У каждого `action` есть имя вызова (`api_name`), процесс (`call_name`, `call_pid`), время (`call_time`), код возврата (`ret_value`), аргументы (`apiArg_list`) и дополнительные сведения (`exInfo_list`, например пути к файлам).

# 3. Правила конвертации

**Таблица 2.** Правила и их обоснование

| № | Правило | Почему |
|:---:|:---|:---|
| 1 | Берётся только имя вызова `api_name`; аргументы, время, коды возврата, имя файла не используются | формат MalBehavD-V1 — только последовательность имён API |
| 2 | Каждое имя API берётся один раз, в порядке первого вызова; хвост строки пустой | так устроен MalBehavD-V1: уникальные API в порядке первого появления |
| 3 | Вызовы из обоих разделов отчёта по порядку: сначала `start_boot`, затем `reboot` | раздел `reboot` — продолжение поведения того же файла |
| 4 | Вызовы всех процессов (исходного и порождённых) в одной последовательности | у MalBehavD-V1 последовательность тоже на файл, а не на процесс |
| 5 | Метка — из `safe_type_train.csv`; папка `black`/`white` — только для сверки | файл меток — первичный источник; расхождения выводятся как проблема |
| 6 | Папка `test/` не используется | у неё нет меток |
| 7 | Два варианта: **raw** — все записи как есть; **clean** — без служебных записей песочницы (всё, что начинается с `Fake_`, и `AnalyzeStart`, `AnalyzeStop`, `TryToAnalyze`, `TooManyBehavior`, `UnpackSelf`) | служебные записи — пометки песочницы, а не вызовы Windows API; заранее неясно, мешают они или помогают, поэтому оставлены оба варианта |
| 8 | Строка, у которой в clean не осталось ни одного вызова, в clean не попадает, но остаётся в `datacon_meta.csv` с `kept_clean = 0` | `audit_duplicates.py` и модели не принимают пустые последовательности |
| 9 | Разбор XML потоковый, в несколько процессов; при ошибке разбора берётся прочитанная часть, файл помечается | отчёты до нескольких МБ, всего 23 ГБ |
| 10 | Кроме последовательностей сохраняются описательные поля отчёта (`datacon_meta.csv`) и словарь (`datacon_vocab.csv`) | нужны для проверки признаков, которые выдают метку без смысла поведения |

## 5.5. Признаки-«подсказки»

**Таблица 11.** Признаки отчёта, не связанные со смыслом поведения

| Признак | benign | malware | Что показано | ROC-AUC одного признака |
|:---|:---:|:---:|:---|:---:|
| Размер XML-отчёта | 39 КБ | 1,10 МБ | медиана | 0,896 |
| Число вызовов (с повторами) | 112 | 2777 | медиана | 0,895 |
| Число процессов | 1 | 20 | медиана | 0,816 |
| Пометка `TooManyBehavior` | 14,6 % | 76,4 % | доля файлов | 0,809 |
| Длина raw (уникальных API) | 17 | 33 | медиана | 0,798 |
| Длина clean | 11 | 25 | медиана | 0,754 |
| Раздел `reboot` есть | 1,2 % | 39,0 % | доля файлов | 0,689 |

ROC-AUC здесь — насколько хорошо один признак сам по себе отделяет malware от benign: 0,5 — никак, 1,0 — идеально. Это описание данных, а не модель.

**Как читать.**

- Объём активности (размер отчёта, число вызовов, число процессов) отделяет классы почти так же хорошо, как хорошие модели. Вредоносный файл в песочнице просто делает намного больше.
- В clean-последовательность объём попадает только косвенно — через длину строки (ROC-AUC 0,754) и через то, какие API встретились. Число вызовов и процессов модель не видит, потому что берутся уникальные API.
- Для честной оценки это значит: высокие метрики на DataCon нужно сравнивать с базовой линией «только по длине последовательности». Если модель лишь немного лучше длины, она, скорее всего, использует подсказку объёма, а не смысл поведения.

# 7. Открытые вопросы и следующие шаги

1. **Согласовать с руководителем**, что DataCon — второй датасет (неделя 5 плана). Тогда повторяются аудит дублей и протоколы A и B на одном варианте, предлагаю clean.
2. **Конфликтующие метки:** исключать до разбиения, как в MalBehavD-V1 (−2010 строк clean), или оставить и описать. Решение фиксируется до построения разбиений.
3. **Список служебных записей:** оставить как есть или добавить вариант с расширенным списком (`StrangeBehavior`, `VMDetect`, `PowerOn` и т. п.) — новым параметром конвертера, не меняя raw и clean.
4. **Базовая линия «только длина последовательности»** — добавить к TF-IDF и GINE, чтобы видеть, насколько модели лучше подсказки объёма.
5. **Разбиения:** построить A и B существующим `make_splits.py` и проверить критерии К1–К3 с учётом крупных benign-групп (до 1103 строк).
6. **Время GINE:** на 30 000 строках обучение на CPU займёт заметно дольше, чем на MalBehavD. Время нужно оценить на одном seed до серии.
